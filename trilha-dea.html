CAP. 01

Fundamentos de engenharia de dados

Alta prioridade

O vocabulário que o exame pressupõe

ConceitoDefinição em uma linha
ETL vs ELTETL transforma ANTES de carregar (Glue → Redshift). ELT carrega cru e transforma DENTRO do destino (S3 → SQL no Redshift/Athena)

OLTP vs OLAPOLTP: transações rápidas linha a linha (RDS, DynamoDB). OLAP: análise agregada em massa, orientada a colunas (Redshift, Athena)
ReplayabilityCapacidade de reprocessar dados já ingeridos (retenção do Kinesis, zona raw imutável no S3) — pré-requisito para recuperar de falhas de pipeline
Stateful vs statelessTransação stateless não depende de contexto anterior (transformar 1 registro); stateful precisa de estado acumulado (janelas, agregações, deduplicação) — Flink e Spark Streaming são stateful

Volume, velocidade e variedade — os 3 Vs que decidem a arquitetura

O exam guide cita explicitamente os 3 Vs como base das decisões. Volume decide entre Lambda (leve) e Spark distribuído (Glue/EMR); volumes enormes com rede lenta levam à família Snow. Velocidade decide entre batch (Glue agendado) e streaming (Kinesis/MSK/Flink); "segundos" é streaming, "minutos" é Firehose/micro-batch, "horas" é batch. Variedade decide o store: estruturado → Redshift/RDS; semiestruturado (JSON) → S3 + Athena, DynamoDB, coluna SUPER no Redshift; não estruturado (imagens, texto livre) → S3 puro. Quando a questão descreve o dado, ela está te dizendo a resposta.

Formatos de arquivo — a decisão mais repetida do exame

FormatoTipoQuando é a resposta

ORCColunarEquivalente ao Parquet, mais comum no ecossistema Hive

★
O mantra do DEAParquet + particionamento + compressão = menos dado escaneado = menos custo + mais performance. Esta é a resposta de otimização padrão em Athena, Redshift Spectrum, Glue e EMR. Quando duas alternativas parecem certas, a que envolve formato colunar e partição costuma vencer.

Compressão — o detalhe que derruba candidatos

CodecSplittable?Característica
SnappySim (dentro de Parquet/ORC)Rápido, taxa moderada — o padrão para analytics
gzipNãoBoa taxa, mas um arquivo .gz gigante não pode ser dividido entre workers → gargalo de paralelismo

⚠
Armadilha de splittability"Um único arquivo CSV de 50 GB comprimido em gzip está lento no processamento" → o problema é que gzip não é divisível: um único worker processa tudo. Solução: dividir em vários arquivos e/ou usar formato colunar com Snappy.

Particionamento estilo Hive

s3://datalake/vendas/ano=2026/mes=06/dia=12/arquivo.parquet
                      └── filtros WHERE ano/mes/dia só leem a pasta certa (partition pruning)

Particione pelas colunas mais usadas em filtros (geralmente data). Cuidado com cardinalidade alta demais: particionar por cliente_id com milhões de clientes cria milhões de pastas minúsculas — o problema dos small files.

SQL — o que a prova espera que você leia

O DEA não cobra sintaxe decorada, mas espera que você leia e interprete queries: JOINs (INNER vs LEFT), GROUP BY com HAVING, subqueries e CTEs (WITH), e window functions — ROW_NUMBER() para deduplicar, SUM() OVER (PARTITION BY...) para acumulados, LAG/LEAD para comparar com a linha anterior. Também espera noções de otimização: filtrar cedo (predicate pushdown), selecionar só as colunas necessárias e evitar SELECT DISTINCT desnecessário em tabelas grandes. O capítulo 12 aprofunda análise com SQL.

Checkpoint de revisão

  • Converter para Parquet (colunar — lê só as colunas necessárias) e particionar por data (partition pruning — lê só as pastas filtradas). Compressão Snappy complementa.
  • Avro — schema embutido e evolução de schema nativa, idealmente com Glue Schema Registry para validar compatibilidade.
  • ETL: Glue/EMR transforma antes de gravar no destino. ELT: carrega cru no S3/Redshift e transforma lá dentro com SQL (CTAS, dbt, stored procedures).
  • Replayability — retenção no Kinesis Data Streams (24h–365d) permite reler o stream; a zona raw imutável no S3 permite reprocessar batch. Por isso a raw nunca deve ser sobrescrita.
  • Stateful — é preciso lembrar o que já passou (estado). Por isso deduplicação em streaming pede Flink/Spark Streaming com estado, não uma Lambda simples por registro.

CAP. 02

Ingestão streaming: Kinesis e MSK

Alta prioridade
Streams quando você precisa de replay/múltiplos consumidores; direto no Firehose quando é só entrega. O Parquet nasce na entrega — não depois.

A decisão central: Data Streams × Firehose × MSK

Kinesis Data StreamsData FirehoseMSK
O que éStream bruto: você produz e consomeServiço de entrega: recebe e deposita no destinoApache Kafka gerenciado
LatênciaTempo real (<1s)Near real-time (buffer mínimo de segundos)Tempo real
ConsumidoresMúltiplos, com replay (retenção 24h–365d)Nenhum — entrega direto no destinoMúltiplos, com replay
GestãoShards (ou on-demand)Zero — totalmente gerenciadoBrokers/tópicos (ou MSK Serverless)
Gatilho na questão"processar em tempo real", "múltiplos consumidores", "reprocessar""só entregar no S3/Redshift sem gerenciar nada""já usa Kafka", "compatibilidade Kafka"
⚠
A pegadinha mais clássica do DEAFirehose NÃO é tempo real — é near real-time (buffer por tamanho ou tempo). Se a questão exige latência de sub-segundo para o consumidor, a resposta é Kinesis Data Streams (ou MSK), nunca Firehose.

Kinesis Data Streams a fundo

ConceitoO que saber para a prova
ShardUnidade de capacidade: 1 MB/s ou 1.000 registros/s de escrita; 2 MB/s de leitura. Escalar = resharding (split/merge)
Partition keyDefine para qual shard o registro vai. Chave mal distribuída → hot shard → ProvisionedThroughputExceeded
Capacity modesOn-demand (escala sozinho, carga imprevisível) vs Provisioned (mais barato para carga estável)
Enhanced fan-out2 MB/s dedicados por consumidor via push — resposta para "vários consumidores com baixa latência"
Retenção24h padrão, extensível até 365 dias — permite replay/reprocessamento
Producers/ConsumersKPL (agregação, mais throughput), SDK, Kinesis Agent | KCL (checkpointing em DynamoDB), Lambda
⚠
Erro ProvisionedThroughputExceededCausas e soluções em ordem: (1) hot partition → melhorar a distribuição da partition key; (2) capacidade insuficiente → aumentar shards ou mudar para on-demand; (3) no producer → retries com backoff exponencial e agregação com KPL.

Lambda como consumidor de Kinesis — o Event Source Mapping

ConfiguraçãoO que faz / gatilho de prova
Batch size / batching windowQuantos registros (até 10.000) ou quanto tempo esperar antes de invocar — throughput maior por invocação
Parallelization factorAté 10 invocações simultâneas por shard — escala o consumo sem reshard; resposta para "IteratorAge alta sem mudar o stream"
On-failure destinationRegistros que falham após os retries vão para SQS/SNS — o "DLQ" do consumo de stream
Bisect batch on errorDivide o lote ao meio a cada falha para isolar o registro venenoso (poison pill)
Maximum retry attempts / record ageLimita reprocessamento infinito de um lote com erro — sem isso, o shard trava no registro que falha

Fan-in e fan-out no streaming

Fan-in (muitas fontes → um canal): milhares de dispositivos/apps escrevendo no mesmo stream — a partition key precisa distribuir bem, e o KPL agrega registros pequenos para não estourar o limite de 1.000 registros/s por shard. Fan-out (um canal → muitos consumidores): consumidores compartilham os 2 MB/s de leitura do shard; com vários consumidores, use Enhanced Fan-Out (2 MB/s dedicados por consumidor, push via HTTP/2) ou distribua via SNS → SQS para consumidores não-streaming. Padrão completo que a prova adora: Kinesis → Firehose (arquivo no lake) e Kinesis → Flink (agregação em tempo real) — dois consumidores do mesmo stream.

DynamoDB Streams — o CDC do DynamoDB

Fluxo ordenado de mudanças (insert/update/delete) de uma tabela DynamoDB, retenção de 24 horas, consumido por Lambda ou KCL. Gatilho: "reagir a cada mudança na tabela DynamoDB" ou "replicar mudanças do DynamoDB para outro sistema". Alternativa moderna: Kinesis Data Streams for DynamoDB — envia as mudanças para um stream Kinesis de verdade (retenção maior, mais consumidores, Firehose direto). Se a questão pede retenção além de 24h ou integração com o ecossistema Kinesis, é essa a resposta.

MSK a fundo

MSK provisionado: você dimensiona brokers e storage — controle total, mais gestão. MSK Serverless: paga por throughput, sem dimensionar brokers — gatilho "Kafka sem gerenciar capacidade". MSK Connect: conectores Kafka Connect gerenciados (ex.: sink para S3) — o "Firehose do mundo Kafka". Segurança cobrada: autenticação IAM access control (a mais simples), SASL/SCRAM (credenciais no Secrets Manager) ou mTLS; criptografia TLS em trânsito e KMS em repouso. Kafka mantém ordem por partição (como o Kinesis por shard).

Data Firehose a fundo

Origem: Direct PUT, Kinesis Data Streams, MSK. Destinos: S3, Redshift, OpenSearch, HTTP endpoints e parceiros. Recursos cobrados em prova: buffer hints (tamanho MB ou intervalo em segundos — o que vier primeiro), transformação via Lambda em trânsito, conversão de formato nativa para Parquet/ORC (exige schema no Glue Catalog), particionamento dinâmico na escrita do S3, e backup de registros com falha em um bucket de erro.

Processamento de stream: Managed Service for Apache Flink

Para analisar/transformar o stream em movimento (janelas de tempo, agregações em tempo real, detecção de anomalias) com SQL ou Java/Python — antigo Kinesis Data Analytics. Gatilho: "agregações por janela de 1 minuto sobre o stream", "detectar padrão em tempo real". Lambda serve para transformações simples por registro; Flink para lógica com estado e janelas. Conceitos de janela que aparecem: tumbling (janelas fixas sem sobreposição — total por minuto), sliding (sobrepostas — média móvel dos últimos 5 min a cada 1 min) e session (agrupa por inatividade — sessões de usuário). O estado do Flink é mantido em checkpoints — é assim que ele retoma sem perder agregações após falha.

Throttling e rate limits — lidando com limites das fontes

O exam guide cobra explicitamente "implementar throttling e superar rate limits". As respostas padrão: retries com backoff exponencial e jitter (todos os SDKs), agregação no producer (KPL no Kinesis), aumentar capacidade (shards/on-demand no Kinesis e DynamoDB), e SQS como amortecedor entre o produtor rápido e o consumidor limitado (ex.: proteger um RDS de rajadas de escrita). Para conectar em fontes externas com firewall, a questão pode pedir IP allowlist: dê IP fixo ao pipeline com NAT Gateway (Elastic IP) e libere esse IP na origem.

Checkpoint de revisão

  • Data Firehose com conversão de formato para Parquet. Zero gestão, entrega gerenciada, buffer configurável.
  • Kinesis Data Streams com Enhanced Fan-Out — 2 MB/s dedicados por consumidor via push, sem competir pelo throughput compartilhado.
  • Hot shard — a partition key está concentrando tráfego em um shard. Solução: usar uma chave com melhor distribuição (ex.: adicionar sufixo aleatório).
  • Managed Service for Apache Flink — processamento com estado e janelas de tempo sobre o stream.
  • Aumentar o parallelization factor do Event Source Mapping (até 10 invocações simultâneas por shard) e/ou o batch size — escala o consumo sem reshard.
  • Bisect batch on error + maximum retry attempts + on-failure destination (SQS) — o lote é dividido até isolar o registro venenoso, que vai para a fila de falhas.

⚠
DMS vs DataSync vs AppFlowDMS = bancos de dados (linhas/tabelas, CDC). DataSync = arquivos (NFS/SMB/objetos). AppFlow = SaaS. A questão sempre revela a origem — basta classificar.

DMS a fundo

Uma instância de replicação executa tasks entre um source endpoint e um target endpoint. Três modos de task: full load (cópia única), full load + CDC (migração sem downtime — copia e depois replica as mudanças) e CDC only (replicação contínua). O CDC lê o log de transações do banco (binlog/WAL/redo log). Migração homogênea (Oracle→Oracle) não precisa de SCT; heterogênea (Oracle→PostgreSQL) exige SCT ou DMS Schema Conversion antes, para converter schema e código. Destino S3: o DMS grava arquivos CSV/Parquet com uma coluna de operação (I/U/D) — para materializar o estado final no lake, um formato transacional (Iceberg) ou merge posterior resolve. Aparece também DMS Serverless: capacidade automática para a task, gatilho "sem dimensionar instância de replicação".

S3 como porta de entrada — recursos de ingestão

S3 Event Notifications → EventBridge/SQS/Lambda: o padrão "chegou arquivo, dispara pipeline". Multipart Upload para arquivos grandes (obrigatório acima de 5 GB; recomendado acima de 100 MB) e Transfer Acceleration para upload de longa distância via edge locations. S3 Batch Operations: aplicar uma operação (copiar, etiquetar, invocar Lambda) sobre bilhões de objetos existentes — gatilho: "processar todos os objetos já existentes no bucket".

Batch agendado vs orientado a evento

O exam guide distingue os dois padrões de ingestão batch. Agendado: EventBridge Scheduler dispara o job às 2h (cron) — simples, mas se o arquivo atrasar o job roda no vazio. Orientado a evento: S3 Event Notification dispara quando o arquivo chega — processa na hora, sem janela morta. A prova favorece o orientado a evento quando o enunciado diz "assim que os dados chegarem" ou "horário de chegada imprevisível"; o agendado quando há dependência de consolidação diária ("fechar o dia às 23h59").

Checkpoint de revisão

  • DMS com CDC (Change Data Capture), destino S3. Full load inicial + CDC contínuo.
  • Amazon AppFlow — conector nativo do Salesforce, agendamento e mapeamento de campos sem código.
  • Integração zero-ETL Aurora → Redshift — replicação contínua gerenciada pela AWS.

DynamicFrame vs DataFrameDynamicFrame é a abstração do Glue: tolera schema inconsistente (campos com tipos mistos viram "choice types") e tem transformações próprias (ResolveChoice, Relationalize). Converta para Spark DataFrame quando precisar da API completa do Spark.

Connections, crawlers e o Catalog na prática

Glue Connections guardam os detalhes de acesso a fontes JDBC (RDS, Redshift, bancos on-premises via VPC): endpoint, credenciais (idealmente via Secrets Manager) e a VPC/subnet/security group por onde o job sai. Jobs que acessam recursos em VPC rodam com ENIs na sua subnet — se o job não alcança a fonte, verifique security group (self-referencing rule) e rota. Crawlers: use exclusions para pular pastas, incremental crawls (só novas partições) para acelerar, e partition indexes em tabelas com muitas partições para acelerar o GetPartitions do Athena. O Catalog é compatível com Apache Hive metastore — EMR e serviços externos podem usá-lo como metastore central. Alternativa a rodar crawler a cada carga: gravar já registrando partições com MSCK REPAIR TABLE/ALTER TABLE ADD PARTITION, ou partition projection no Athena.

Detecção de dados sensíveis (PII) no Glue

A transformação Detect PII em jobs Glue identifica dados sensíveis (CPF, e-mail, cartão) durante o ETL e pode mascarar/redigir as colunas na escrita. Arquitetura de zonas

Otimização de arquivos — o problema dos small files

⚠
Small files problemMilhões de arquivos de poucos KB matam a performance de Athena/Spark/EMR — o overhead de abrir cada arquivo supera o tempo de leitura. Tamanho ideal: ~128 MB a 1 GB por arquivo. Soluções: aumentar buffer do Firehose, compaction periódica (job Glue/Spark com coalesce, ou compaction automática de tabelas Iceberg).

Performance do S3 para o lake

O S3 entrega 3.500 PUT/s e 5.500 GET/s por prefixo — e escala horizontalmente com mais prefixos: paralelizar leituras por muitos prefixos multiplica o throughput (por isso o particionamento também ajuda a performance de I/O, não só o pruning). Para arquivos grandes, multipart upload na escrita e byte-range fetches na leitura paralela. Se a questão fala em "milhares de requisições por segundo num único prefixo com throttling 503", a resposta é distribuir as chaves em mais prefixos.

Formatos de tabela transacionais (lakehouse)

TecnologiaO que adiciona ao data lake

Apache Hudi / Delta LakeMesma categoria — aparecem como alternativas, principalmente no EMR

O que saber do Iceberg além do conceito: cada escrita cria um snapshot — time travel é consultar um snapshot antigo (FOR TIMESTAMP AS OF no Athena); schema evolution real (adicionar/renomear/remover coluna sem reescrever dados); e manutenção: compaction (OPTIMIZE ... REWRITE DATA no Athena resolve small files) e expiração de snapshots antigos (VACUUM) para conter custo de storage. Tabelas Iceberg são criadas no próprio Glue Catalog e funcionam com Athena, Glue, EMR e Redshift.

Modelagem de dados e evolução de schema

Consolidar

A Task 2.4 do exam guide cobra modelagem: schemas para Redshift, DynamoDB e Lake Formation, evolução de schema e linhagem. É o capítulo que separa "conheço os serviços" de "sei desenhar o dado dentro deles".

Star schema — o modelo do warehouse

                dim_data      dim_produto
                      \\            /
                   ┌────────────────┐
                   │  fato_vendas   │  ← métricas (valor, qtd) + FKs
                   └────────────────┘
                      /            \\
                dim_cliente     dim_loja

A tabela fato guarda eventos/métricas (grande, cresce sempre); as dimensões guardam contexto descritivo (pequenas, mudam pouco). No Redshift: fato com DISTKEY na coluna de join mais usada e SORTKEY na data; dimensões pequenas com DISTSTYLE ALL. Snowflake schema = dimensões normalizadas em sub-dimensões — menos redundância, mais JOINs; a prova prefere star para BI. Desnormalizar (juntar tudo numa tabela larga) é aceitável em warehouse colunar: colunas não consultadas não são lidas — o custo da redundância é menor que o custo dos JOINs.

Normalização vs desnormalização — OLTP vs OLAP

Normalizado (3FN)Desnormalizado
OndeOLTP — RDS/AuroraOLAP — Redshift, data lake
OtimizaEscritas consistentes, sem redundânciaLeituras analíticas, menos JOINs
Trade-offMuitos JOINs para consultarRedundância controlada (barata em colunar)

Modelagem no DynamoDB — o oposto do relacional

No DynamoDB você modela pelos padrões de acesso, não pelas entidades: primeiro liste as queries ("buscar pedidos do cliente X por data"), depois desenhe a chave. Partition key de alta cardinalidade e acesso uniforme (evitar hot partition); sort key para ordenar/filtrar dentro da partição (begins_with, between); GSI para consultar por outro atributo (projete só as colunas necessárias); single-table design agrupa entidades relacionadas na mesma tabela usando chaves compostas — o padrão para "buscar cliente + pedidos numa única query". Scan é sempre a alternativa errada em tabela grande.

Evolução de schema — quando o dado muda de forma

CenárioMecanismo

Coluna nova aparece nos arquivos do lakeParquet + crawler com política de update do schema; ou Iceberg, que evolui schema por metadados sem reescrever dados
Tipos mistos no mesmo campo (int vira string)Glue DynamicFrame choice types + ResolveChoice

Linhagem de dados (data lineage)

Linhagem responde "de onde veio este número?": fonte → transformações → destino. No contexto da prova: SageMaker ML Lineage Tracking (citado nominalmente no exam guide) rastreia linhagem de artefatos de ML; no pipeline clássico, a linhagem prática vem de metadados do Glue Catalog, tags, e do histórico de jobs/steps (Glue/Step Functions). O conceito importa mais que a ferramenta: linhagem dá confiança e auditabilidade ao dado.

Checkpoint de revisão

  • Star schema: DISTKEY na coluna de join da fato, DISTSTYLE ALL nas dimensões pequenas, SORTKEY na coluna de data da fato. JOINs viram operações locais em cada slice.
  • Glue Schema Registry com regra de compatibilidade (ex.: backward) — o registry rejeita a publicação de schema incompatível antes de chegar aos consumers.
  • Partition key = cliente_id, sort key = data do pedido — Query com condição de faixa na sort key. Nunca Scan com filtro.
  • AWS SCT (ou DMS Schema Conversion) para converter schema/código; depois DMS full load + CDC para migrar os dados sem downtime.

Alta prioridade
MPP na prática: o leader planeja, os slices executam em paralelo. Distribuição e ordenação são as duas alavancas de performance.

Carga e descarga de dados

★

Programando o Redshift: stored procedures e Data API

O padrão ELT completo: COPY carrega a staging → stored procedure transforma → Step Functions orquestra via Data API.

Locks e concorrência

O exam guide cita "manage locks". Sintoma clássico em prova: "uma transação aberta há horas está bloqueando o ETL" → identificar e terminar a sessão. Boas práticas: transações curtas, COPY em vez de muitos INSERTs, e janelas de manutenção para DDL.

Use EMRFS (dados no S3) em vez de HDFS para desacoplar storage de compute — clusters transientes que sobem, processam e morrem são o padrão de custo. EMR Serverless: submeter jobs Spark/Hive sem dimensionar cluster nenhum. EMR on EKS: rodar Spark no cluster Kubernetes existente. Dimensionamento: instance fleets misturam tipos de instância e estratégias Spot/On-Demand; managed scaling ajusta o cluster à carga automaticamente. Automação: steps submetem trabalhos em sequência (cluster transiente com auto-terminate após o último step); bootstrap actions instalam dependências na subida do cluster.

Spark essencial para a prova

O exam guide cobra "como usar Apache Spark para processar dados". O modelo: um driver coordena executors que processam partições em paralelo. Transformações são lazy — só executam na ação (write, count). O vilão de performance é o shuffle (redistribuir dados entre executors em joins/groupBy) — e o vilão do shuffle é o data skew: uma chave dominante concentra tudo num executor (job "para" em 99%, um executor com OOM). Mitigações que aparecem em prova: salting (sufixo aleatório na chave quente), broadcast join (tabela pequena copiada para todos os executors — elimina o shuffle do join), repartition/coalesce para controlar partições antes da escrita (evita small files), e cache apenas do que é reutilizado. No Glue, as mesmas ideias valem — mudam só os nomes (workers em vez de executors).

  • Broadcast join — a tabela pequena é replicada para todos os executors e o join vira operação local, sem shuffle.

Step Functions: Standard vs ExpressStandard: até 1 ano de duração, exactly-once, auditável passo a passo — pipelines de dados. Express: alto volume, curto (até 5 min), at-least-once, mais barato — ingestão de eventos em massa.

Step Functions — os estados que caem em prova

Task chama o serviço (com .sync para esperar o Glue Job/EMR step terminar — sem polling manual); Choice ramifica; Parallel executa ramos simultâneos; Map itera sobre uma lista — e o Distributed Map processa milhões de objetos S3 em paralelo massivo (gatilho: "processar milhões de arquivos em paralelo com orquestração serverless"). Retry com backoff e Catch roteando para um ramo de erro são o coração do tratamento de falhas. Wait/callback com task token cobre aprovações humanas ou espera por evento externo.

MWAA — quando o Airflow é a resposta

DAGs Python no S3, executados por um ambiente Airflow gerenciado (scheduler + workers com auto scaling; você escolhe a classe do ambiente). MWAA não é serverless — tem custo fixo por hora. Por isso a decisão de prova: pipelines novos 100% AWS → Step Functions (serverless, integrações nativas); time que já tem DAGs/expertise Airflow ou precisa dos milhares de operadores da comunidade → MWAA. Troubleshooting comum: DAG não aparece (erro de sintaxe/import — ver logs do scheduler no CloudWatch), tasks na fila sem executar (workers no limite — aumentar auto scaling).

Alerta de falha de pipeline — o padrão completo

Glue Job FAILED → EventBridge rule (event pattern: glue job state change)

Vale para Glue, Step Functions (Execution Status Change), EMR e MWAA. A prova pergunta "como ser notificado quando o job falhar, sem polling" — EventBridge + SNS é a resposta; polling de status via script é sempre a alternativa errada.

Otimização de código e SQL — os princípios

Lake Formation — o centro da governança

O IAM controla acesso a serviços e recursos; o Lake Formation controla acesso a dados do lake com granularidade que o IAM sozinho não alcança: database, tabela, coluna, linha e célula. Autenticação e IAM no contexto de dados

Roles, nunca chaves de acesso: Glue Job, Lambda e EMR assumem roles — credenciais hardcoded são sempre a alternativa errada. AWS managed policies (prontas, genéricas) vs customer managed policies (suas, com least privilege — a resposta quando a managed dá permissão demais). Cross-account: a conta A assume uma role na conta B (trust policy) — o padrão para pipeline de uma conta ler dados de outra; para S3, também bucket policy concedendo à role externa, ou S3 Access Points para gerenciar múltiplos consumidores de um mesmo bucket com políticas separadas por ponto de acesso.

Rede segura para o dado — VPC

VPC Endpoints: Gateway (S3, DynamoDB — grátis) e Interface/PrivateLink (Glue, Kinesis, Redshift, Athena, Secrets Manager) mantêm o tráfego fora da internet — o requisito "os dados não podem trafegar pela internet pública" se resolve aqui, com endpoint policies restringindo o que passa. Security groups: stateful; para o Glue acessar um RDS na VPC, a regra clássica é o security group self-referencing exigido pela Glue Connection. IP allowlist em fonte externa: NAT Gateway com Elastic IP dá IP fixo de saída ao pipeline.

Criptografia — client-side vs server-side e cross-account

Server-side (SSE): a AWS criptografa ao receber — SSE-S3 (chave da AWS, zero gestão), SSE-KMS (sua CMK, auditoria por CloudTrail, controle de acesso por key policy — a resposta quando há requisito de auditoria/controle), SSE-C (você envia a chave a cada request — raro). Client-side: o dado sai da sua aplicação já criptografado (KMS keyring/Encryption SDK) — a resposta quando "os dados devem estar criptografados antes de deixar a aplicação" ou quando nem a AWS pode ver o conteúdo. Cross-account com KMS: para a conta B ler objetos SSE-KMS da conta A, além do acesso ao bucket, a key policy precisa conceder kms:Decrypt à role da conta B — a pegadinha clássica do "AccessDenied mesmo com bucket policy correta".
