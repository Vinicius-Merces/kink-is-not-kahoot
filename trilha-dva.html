CAP. 01

Fundamentos do desenvolvedor AWS — SDK, CLI e credenciais

Alta prioridade

A cadeia de credenciais (credential provider chain)

Quando seu código usa o SDK ou a CLI, a AWS procura credenciais em uma ordem fixa — e o exame adora perguntar "de onde vieram as credenciais" ou "qual é a forma mais segura". A ordem simplificada:

OrdemFonteNota de prova
1Opções de linha de comando / parâmetros explícitos no códigoHardcoded no código = sempre a alternativa errada
2Variáveis de ambiente (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY)Comum em CI/CD e containers
3Arquivos de perfil (~/.aws/credentials e ~/.aws/config)Uso local do desenvolvedor; suporta múltiplos profiles (--profile)
4Credenciais de container (ECS task role)Para tasks no ECS/Fargate
5Instance Profile via IMDS (EC2)A resposta certa para código rodando em EC2: role anexada, credenciais temporárias, rotação automática
🪤
Armadilha clássica"A aplicação em EC2 precisa acessar o S3, qual a forma MAIS SEGURA?" — a resposta é sempre IAM Role anexada à instância (Instance Profile), nunca access keys em variável de ambiente, arquivo de configuração ou (pior) no código. Em Lambda, o equivalente é a Execution Role; em ECS, a Task Role.

Retries, throttling e exponential backoff

Toda API da AWS pode responder com throttling (HTTP 429 / ThrottlingException / ProvisionedThroughputExceededException). O SDK já faz retry automático com exponential backoff (espera 1s, 2s, 4s, 8s...). O refinamento que o exame cobra é o jitter: adicionar aleatoriedade às esperas para que milhares de clientes não tentem de novo ao mesmo tempo (o efeito "manada").

SintomaResposta esperada
Erros 429/throttling intermitentesExponential backoff com jitter (o SDK já implementa — não desative)
Erros 5xx da API da AWSRetry é apropriado (falha transitória do servidor)
Erros 4xx de validação (400, 403)NÃO adianta retry — corrija a requisição/permissão
Operação repetida por retry causa efeito duplicadoTorne a operação idempotente (ex.: client token, chave condicional)

Regiões, endpoints e paginação

Três pontos rápidos que rendem questões: (1) o SDK precisa de uma Região definida (env AWS_REGION, config ou código) — "endpoint não encontrado" costuma ser Região errada; (2) chamadas de listagem são paginadas (use os paginators do SDK em vez de loops manuais com NextToken); (3) para testar permissões sem executar, a CLI tem --dry-run em várias operações do EC2.

Padrões de arquitetura — o vocabulário da Task 1.1

ConceitoO que saber para a prova
Event-drivenComponentes reagem a eventos em vez de se chamarem diretamente (S3 Event → Lambda; EventBridge roteando). Escala e desacopla — é a resposta padrão para "reduzir acoplamento"
Microsserviços vs monolitoServiços pequenos com deploy independente vs aplicação única. "Times independentes, deploys separados, escalar partes isoladamente" = microsserviços
Coreografia vs orquestraçãoCoreografia: cada serviço reage a eventos, sem coordenador central (EventBridge/SNS). Orquestração: um coordenador central dirige o fluxo (Step Functions). "Fluxo complexo com estado e tratamento de erro central" = orquestração
Acoplamento forte vs fracoChamada síncrona direta = forte (falha propaga). Fila/evento no meio = fraco (falha isolada, retry natural). SQS é a resposta clássica de desacoplamento
Síncrono vs assíncronoSíncrono: o chamador espera a resposta. Assíncrono: aceita (202) e processa depois — o padrão para trabalho demorado, picos e resiliência
IdempotênciaProcessar a mesma requisição 2x produz o mesmo resultado — obrigatório onde há retry (SQS entrega at-least-once). Implementação típica: chave de idempotência + condition expression no DynamoDB
Fan-out1 evento → N consumidores independentes: SNS → múltiplas SQS (durabilidade por consumidor)
💡
Stateless primeiroO exame favorece componentes stateless (estado fora, em DynamoDB/ElastiCache/S3) porque escalam horizontalmente sem sessão presa. Se a questão menciona "instâncias guardam estado local e usuários perdem sessão", a resposta envolve externalizar o estado — nunca sticky sessions como solução definitiva.

Checkpoint de revisão

  • IAM Role anexada à instância (Instance Profile). O SDK obtém credenciais temporárias automaticamente via IMDS, com rotação automática — sem chaves de longo prazo armazenadas.
  • Exponential backoff com jitter — aumentar progressivamente o intervalo entre retries com aleatoriedade. O SDK da AWS já faz isso por padrão.
  • Variáveis de ambiente vêm antes; o Instance Profile (IMDS) é a última fonte consultada. Por isso uma env var esquecida pode "sobrepor" a role da instância.

CAP. 02

AWS Lambda a fundo

Alta prioridade
Quem chama define o modo — e o modo define o comportamento em erro. Decore as três colunas.

Os números que caem na prova

LimiteValorPor que importa
Timeout máximo15 minutos (900s)Tarefa mais longa? Fargate, Batch ou Step Functions
Memória128 MB a 10.240 MBCPU e rede escalam JUNTO com a memória — função lenta de CPU? Aumente a memória
/tmp (armazenamento efêmero)512 MB a 10 GBArquivo temporário grande? Configure o /tmp ou use EFS montado
Payload síncrono6 MBArquivo maior? Passe via S3 (presigned URL), não no payload
Deploy (zip)50 MB direto / 250 MB descomprimidoMaior? Imagem de container (até 10 GB) ou layers
Variáveis de ambiente4 KB no totalSegredos grandes? Secrets Manager / Parameter Store

Invocação síncrona vs assíncrona vs event source mapping

ModoQuem usaComportamento em erro
Síncrona (RequestResponse)API Gateway, ALB, invocação diretaO erro volta para o chamador — retry é responsabilidade do cliente
Assíncrona (Event)S3, SNS, EventBridgeLambda tenta 2 retries automáticos; depois envia para DLQ ou Destinations (on-failure/on-success)
Event Source Mapping (poll)SQS, Kinesis, DynamoDB StreamsO Lambda faz polling na fonte; em streams, um lote com erro bloqueia o shard até resolver (use bisect, DLQ de lote, maxRetryAttempts)
🪤
Armadilha: Destinations vs DLQDLQ (SQS/SNS) recebe só o evento em falha de invocações assíncronas. Lambda Destinations é mais novo e mais rico: rotea sucesso E falha, com contexto completo (request + response), para SQS, SNS, EventBridge ou outra Lambda. Se a questão pede "registro do resultado com detalhes do erro", a resposta é Destinations.

Versions, aliases e tráfego canário

Publicar uma version congela código + configuração (imutável, numerada; $LATEST é a versão mutável de trabalho). Um alias é um ponteiro nomeado para uma versão (ex.: prod → v42) — e aceita pesos de tráfego entre duas versões (ex.: 90% v42, 10% v43) para deploy canário. O CodeDeploy automatiza esse shifting com rollback automático em alarme do CloudWatch.

Concorrência: reserved vs provisioned

RecursoO que fazQuando é a resposta
Reserved ConcurrencyReserva (e LIMITA) o máximo de execuções simultâneas da funçãoProteger um banco a jusante de sobrecarga; garantir capacidade contra outras funções; custo zero
Provisioned ConcurrencyMantém N ambientes pré-inicializadosEliminar cold starts em APIs sensíveis a latência; tem custo por hora
💡
Cold start em VPCLambda em VPC usa ENIs compartilhadas (Hyperplane) — o custo de rede melhorou muito, mas o exame ainda cobra: função em VPC não tem internet sem NAT Gateway + rota, e para acessar S3/DynamoDB o caminho barato é Gateway VPC Endpoint.

Layers e permissões

Layers empacotam dependências compartilhadas entre funções (até 5 por função). Sobre permissões, memorize o par: a Execution Role é o que a FUNÇÃO pode fazer (ex.: escrever no DynamoDB); a Resource-based policy é QUEM pode invocar a função (ex.: permitir que o S3 de outra conta a invoque via lambda:InvokeFunction).

Checkpoint de revisão

  • Aumentar a memória configurada — CPU (e largura de rede) escalam proporcionalmente à memória no Lambda.
  • Provisioned Concurrency — mantém ambientes de execução pré-aquecidos. (Reserved Concurrency limita/reserva quantidade, mas não elimina cold start.)
  • Publicar uma version, usar um alias com pesos de tráfego (weighted alias) entre a versão atual e a nova — idealmente orquestrado pelo CodeDeploy com alarmes do CloudWatch para rollback.
  • Lambda Destinations (on-failure) — invocação do S3 é assíncrona; após os 2 retries, o evento com request/response vai ao destino configurado (SQS, SNS, EventBridge, Lambda).

CAP. 03

Amazon API Gateway

Alta prioridade

REST API vs HTTP API

AspectoREST APIHTTP API
Custo/latênciaMaiorAté ~70% mais barata e mais rápida
RecursosCaching, API keys/usage plans, request validation, canary, WAFEssencial: proxy Lambda/HTTP, JWT authorizer nativo, CORS simples
Quando escolherPrecisa de cache, chaves por cliente, throttling por plano, validaçãoProxy simples e barato para Lambda/microsserviço

Autorização: as quatro portas

MecanismoComo funcionaQuando é a resposta
IAM (SigV4)Requisição assinada com credenciais AWSChamadores internos/serviços com roles IAM
Cognito User Pool AuthorizerValida o JWT emitido pelo user poolApps com usuários finais autenticados no Cognito
Lambda AuthorizerFunção customizada valida token/headers e devolve uma policyAuth de terceiros/legado (OAuth externo, tokens proprietários)
API Keys + Usage PlansChave identifica o cliente; plano define rate/quotaMedir e limitar consumo por cliente — não é autenticação de usuários

Códigos de erro que o exame cobra de cabeça

CódigoSignificado no API Gateway
429Throttling — limite de taxa/burst ou quota do usage plan excedidos
502 Bad GatewayResposta malformada da integração (ex.: Lambda proxy retornou JSON fora do formato statusCode/body)
504 Gateway TimeoutIntegração estourou o timeout do API Gateway — máximo de 29 segundos
403Negado por authorizer/resource policy/WAF, ou API key ausente/inválida
🪤
Armadilha dos 29 segundosLambda aguenta 15 minutos, mas atrás do API Gateway a resposta precisa voltar em 29s. Processo longo via API? Padrão assíncrono: a API enfileira (SQS) ou dispara Step Functions e responde 202 com um ID para consulta posterior — nunca "aumentar o timeout da API para 15 minutos" (não existe).

Stages, canary, cache e CORS

Deploys vão para stages (dev, prod), com stage variables para apontar integrações diferentes (ex.: alias da Lambda por ambiente). Canary release no stage divide o tráfego entre a versão atual e a nova. O cache (REST API) é por stage, com TTL padrão de 300s e invalidação por header Cache-Control: max-age=0 (exige permissão). Erro de CORS no navegador (chamada de outro domínio) se resolve habilitando CORS na API — respostas OPTIONS/preflight com Access-Control-Allow-Origin.

Checkpoint de revisão

  • A função retornou resposta fora do formato exigido pelo proxy (JSON com statusCode, headers e body string) — por exemplo, lançou exceção não tratada ou devolveu objeto cru.
  • Assíncrono: a API aceita a requisição (202) e enfileira no SQS ou inicia uma Step Function; o cliente consulta o status depois. O limite de 29s do API Gateway impede a resposta síncrona.
  • Cognito User Pool Authorizer — o API Gateway valida o token JWT do user pool automaticamente, sem código próprio.
  • API Keys associadas a Usage Plans com throttling e quota por cliente (REST API). Lembrando: API key identifica e limita, não autentica usuários finais.

CAP. 04

DynamoDB para desenvolvedores

Alta prioridade

O cálculo de RCU/WCU — a conta que VAI cair

UnidadeRegra
1 RCU1 leitura fortemente consistente/s de item até 4 KB — ou 2 leituras eventualmente consistentes/s
1 WCU1 escrita/s de item até 1 KB
ArredondamentoTamanho do item SEMPRE arredonda para cima (leitura em blocos de 4 KB, escrita em blocos de 1 KB)
TransaçõesConsomem o dobro (2x RCU/WCU)
🧮
Exemplo resolvido10 leituras fortemente consistentes por segundo de itens de 6 KB: 6 KB arredonda para 8 KB = 2 blocos de 4 KB → 2 RCU por leitura × 10 = 20 RCU. Se fossem eventualmente consistentes: metade = 10 RCU. Escrever 6 itens/s de 2,5 KB: 2,5 KB arredonda para 3 blocos de 1 KB → 3 WCU × 6 = 18 WCU.

GSI vs LSI

AspectoGSI (Global Secondary Index)LSI (Local Secondary Index)
ChavePartition key E sort key novasMESMA partition key, sort key diferente
CriaçãoA qualquer momentoSó na criação da tabela
ConsistênciaApenas eventualForte ou eventual
CapacidadePrópria (throttling no GSI pode travar escrita na tabela!)Compartilha a da tabela

Escritas seguras: condition expressions e locking otimista

Condition expressions tornam a escrita condicional: attribute_not_exists(pk) evita sobrescrever item existente; comparar um atributo version implementa optimistic locking (a escrita falha com ConditionalCheckFailedException se outro processo alterou o item antes). É a resposta padrão para "dois usuários editando o mesmo registro".

Streams, TTL e DAX

RecursoUso de prova
DynamoDB StreamsFluxo ordenado de mudanças (24h) — aciona Lambda para reagir a inserts/updates (ex.: replicar, notificar, agregar)
TTLExpira itens automaticamente por timestamp (epoch) SEM consumir WCU — sessões, caches, dados temporários
DAXCache gerenciado do DynamoDB, leituras em microssegundos, write-through, compatível com a API — para leitura repetitiva intensa (hot items)
BatchGetItem / BatchWriteItemAté 100 leituras / 25 escritas por chamada; itens que falharem voltam em UnprocessedKeys/Items — reenvie com backoff
🪤
Query vs Scan (de novo, porque cai)Scan lê a tabela INTEIRA (o FilterExpression filtra DEPOIS da leitura — paga tudo). Se a consulta é por atributo que não é chave, a resposta é criar um GSI e usar Query. Para acelerar um Scan legítimo (ex.: exportação), use Parallel Scan (Segments/TotalSegments).

ElastiCache — as estratégias de cache que o guide cita nominalmente

EstratégiaComo funcionaTrade-off
Lazy loading (read-through/cache-aside)Busca no cache; miss → lê do banco e grava no cacheSó cacheia o que é lido (eficiente), mas o primeiro acesso é lento e o dado pode ficar stale
Write-throughToda escrita atualiza banco E cache juntosCache sempre atual, mas escreve mais (dados nunca lidos ocupam cache) — combine com lazy loading
TTLExpiração por tempo em cada chaveO corretivo do stale: equilibra frescor vs taxa de miss — a resposta que complementa qualquer estratégia

Redis vs Memcached em uma linha: Redis tem persistência, replicação/failover, estruturas ricas e pub/sub — é a resposta padrão; Memcached é cache puro multi-thread, simples, sem persistência ("cache mais simples possível, escala horizontal"). MemoryDB é o Redis durável usado como banco primário. E lembre a diferença de papel: DAX é só para DynamoDB (write-through, API compatível); ElastiCache é genérico (RDS, APIs, sessões).

Checkpoint de revisão

  • Passo a passo: 5 KB arredonda para 2 blocos de 4 KB → 2 RCU por leitura fortemente consistente. 20 leituras/s × 2 = 40 RCU (forte). Como são eventualmente consistentes, divide por 2 = 20 RCU. Fórmula: (blocos de 4 KB × taxa), ÷ 2 se eventual, × 2 se transação.
  • Optimistic locking com condition expression: gravar somente se o atributo version ainda for o lido (a escrita concorrente falha com ConditionalCheckFailedException e o app decide como resolver).
  • DAX — cache nativo do DynamoDB, compatível com a API existente, com write-through e leituras em microssegundos.
  • DynamoDB Streams com event source mapping para Lambda — a função recebe lotes de mudanças na ordem, por shard.

S3 para desenvolvedores

Alta prioridade

Upload e download do jeito certo

CenárioRecursoDetalhe de prova
Usuário faz upload/download direto sem passar pelo backendPresigned URLURL temporária assinada com as credenciais de quem gerou — herda as permissões dessa identidade e expira
Arquivos grandesMultipart UploadRecomendado > 100 MB, OBRIGATÓRIO > 5 GB; partes em paralelo, retomável; limpe uploads incompletos com lifecycle rule
Upload de milhares de clientes distantesTransfer AccelerationSobe pela edge location mais próxima
Reagir a novos objetosEvent NotificationsS3 → Lambda/SQS/SNS ou EventBridge (mais filtros e destinos)

Criptografia: as quatro siglas

ModoQuem gerencia a chaveQuando é a resposta
SSE-S3 (AES-256)S3, transparentePadrão atual; "criptografia sem gerenciar nada"
SSE-KMSKMS (CMK sua ou da AWS)Auditoria de uso da chave (CloudTrail), controle de acesso à chave, rotação
SSE-CVOCÊ envia a chave em cada request (HTTPS)Compliance exige chave própria fora da AWS; a AWS não a armazena
Client-sideVocê, antes do uploadA AWS nunca vê o dado em claro
🪤
Armadilha do SSE-KMS em escalaCada GET/PUT com SSE-KMS chama o KMS (Decrypt/GenerateDataKey) — e o KMS tem cota de requisições por segundo. Aplicação de altíssimo TPS tomando throttling do KMS ao ler do S3? A resposta é S3 Bucket Keys (reduz drasticamente as chamadas ao KMS) ou aumentar a cota. Erros 403 com SSE-KMS geralmente são falta de permissão kms:Decrypt na role, não no bucket.

CORS e consistência

Front-end em um domínio consumindo bucket/API em outro → erro de CORS no navegador → configure as regras de CORS no bucket (AllowedOrigins/Methods/Headers). Sobre consistência: o S3 hoje é fortemente consistente para leituras após escrita (read-after-write), incluindo sobrescritas e deleções — questões antigas sobre "consistência eventual do S3" estão desatualizadas.

Checkpoint de revisão

  • Backend gera uma presigned URL (ou presigned POST) e o app faz multipart upload direto ao S3 — o backend nunca toca nos bytes.
  • SSE-KMS com customer managed key — cada operação com a chave aparece no CloudTrail; SSE-S3 não dá essa auditoria por chave.
  • Habilitar S3 Bucket Keys no bucket — uma chave de bucket temporária reduz as chamadas ao KMS em até ~99%, aliviando a cota.

Mensageria e Step Functions

Alta prioridade

SQS — os parâmetros que caem

ParâmetroValorQuestão típica
Visibility TimeoutPadrão 30s, máx 12h"Mensagens processadas em duplicidade" = timeout menor que o tempo de processamento → aumente (ou estenda via ChangeMessageVisibility)
Long PollingWaitTimeSeconds até 20s"Reduzir custo/chamadas vazias de ReceiveMessage" = long polling
DLQ + maxReceiveCountApós N recebimentos sem delete, vai para a DLQ"Isolar mensagens venenosas (poison pill)"
Tamanho máximo256 KBMaior? Extended Client Library (payload no S3, ponteiro na fila)
FIFOOrdem + exactly-once por MessageGroupIdDedup por MessageDeduplicationId ou content-based; throughput menor que Standard

SNS e EventBridge — distribuir eventos

SNS é pub/sub push com fan-out (o padrão SNS → múltiplas filas SQS aparece MUITO: durabilidade + consumidores independentes) e filter policies por atributo da mensagem — o guide cita "subscription filter policies para otimizar mensageria": filtrar no SNS evita que cada consumidor receba e descarte o que não é dele. EventBridge é o barramento de eventos com regras de padrão de conteúdo (filtra pelo corpo do evento), integrações SaaS, Scheduler, archive/replay e transformação de entrada — quando a questão fala em "rotear eventos por conteúdo para vários alvos" ou "eventos de terceiros", é EventBridge.

Kinesis para o desenvolvedor

O DVA cobra "handling data streaming": Kinesis Data Streams com shards (1 MB/s in, 2 MB/s out por shard), partition key decidindo o shard (chave quente = ProvisionedThroughputExceededException → melhorar distribuição), ordem garantida por shard, e consumo via Lambda event source mapping (batch, parallelization factor, bisect on error — o mesmo ESM do capítulo 2). Diferença-chave para SQS: Kinesis retém e permite reler (replay, múltiplos consumidores); SQS deleta ao consumir (um consumidor). "Vários consumidores lendo o mesmo fluxo em tempo real" = Kinesis; "distribuir trabalho para workers" = SQS.

AppSync em uma dose

AWS AppSync é GraphQL gerenciado: o cliente pede exatamente os campos de que precisa em uma chamada (menos round-trips que REST), com subscriptions para tempo real via WebSocket e resolvers para DynamoDB/Lambda. Gatilhos de prova: "app mobile com dados em tempo real (chat, colaboração)" ou "reduzir over-fetching de múltiplas APIs REST" → AppSync.

Step Functions — orquestração com estado

ConceitoO que saber
Standard vs ExpressStandard: até 1 ano, exactly-once, auditável — fluxos longos. Express: até 5 min, altíssimo volume, mais barato — ingestão/IoT
States principaisTask (trabalho), Choice (if/else), Wait, Parallel (ramos simultâneos), Map (iterar sobre lista), Pass, Succeed/Fail
Tratamento de erroRetry (com ErrorEquals, IntervalSeconds, BackoffRate, MaxAttempts) e Catch (desvia para estado de tratamento) — a resposta para "retry com backoff SEM escrever código"
CallbacksTask com .waitForTaskToken pausa até um SendTaskSuccess/Failure — aprovação humana ou integração externa
💡
Regra de eliminaçãoEncadear Lambdas chamando Lambda diretamente = acoplamento e sem retry gerenciado → a alternativa com Step Functions vence para workflows de múltiplas etapas com decisões e tratamento de erro. Para simples desacoplamento produtor/consumidor, SQS. Para 1 evento → N interessados, SNS/EventBridge.

Checkpoint de revisão

  • Visibility timeout (padrão 30s) menor que o tempo de processamento — a mensagem reaparece antes do delete. Aumente o visibility timeout (ou estenda durante o processamento).
  • Fan-out: SNS publica e três filas SQS assinam (cada serviço consome a sua) — durabilidade, retry e independência entre consumidores.
  • Step Functions Standard — estados Task com Retry/Catch e callback com task token para a etapa de aprovação humana (pode esperar até 1 ano).
  • SQS Extended Client Library: o payload vai para o S3 e a fila carrega só a referência (limite nativo do SQS é 256 KB).

Segurança para devs — IAM, STS, KMS e segredos

Alta prioridade

IAM na prática do desenvolvedor

Policies em JSON com Effect/Action/Resource/Condition; a avaliação é deny explícito > allow > deny implícito. Para acesso temporário entre contas ou elevação controlada: STS AssumeRole devolve credenciais temporárias (o par confiança da role + permissão sts:AssumeRole do chamador). Para depurar "por que o acesso foi negado", o IAM Policy Simulator é a ferramenta citada em prova.

KMS — envelope encryption e os 4 KB

APIO que fazQuando usar
Encrypt / DecryptCriptografa direto com a CMKSó para dados de até 4 KB
GenerateDataKeyDevolve uma data key em claro + criptografadaEnvelope encryption: cifre o dado grande localmente com a data key, guarde a versão criptografada dela junto do dado; para ler, Decrypt na data key e decifre localmente
GenerateDataKeyWithoutPlaintextSó a versão criptografadaQuando a cifragem ocorrerá depois/em outro lugar
🪤
"Como criptografar um arquivo de 100 MB com KMS?"A resposta NUNCA é chamar Encrypt com o arquivo (limite de 4 KB). É envelope encryption com GenerateDataKey — o padrão que o SDK de criptografia e o próprio S3/SSE-KMS usam por baixo.

Secrets Manager vs Parameter Store

AspectoSecrets ManagerSSM Parameter Store
CustoPago por segredo + API callsStandard: gratuito
Rotação automáticaNativa (com Lambda), integração RDS/Redshift/DocumentDBNão nativa (dá para montar com EventBridge + Lambda)
Uso típicoCredenciais de banco com rotação obrigatóriaConfigurações da aplicação, strings, SecureString com KMS

Regra de prova: a palavra "rotação automática de credenciais" aponta para Secrets Manager; "parâmetros de configuração baratos/hierárquicos (/app/prod/db-url)" aponta para Parameter Store.

Rotação de chaves e certificados

Rotação no KMS: customer managed keys aceitam rotação automática anual (habilitável/desabilitável — o guide cita exatamente isso); as versões antigas da chave ficam disponíveis para descriptografar dados antigos, então nada quebra. Chave com material importado NÃO tem rotação automática. Certificados: o ACM emite e renova certificados TLS públicos de graça (para ALB, CloudFront, API Gateway) — renovação automática é o motivo de prova; o AWS Private CA emite certificados privados para comunicação interna serviço-a-serviço (mTLS, microsserviços) — "certificados para hosts internos que não são públicos" = Private CA. Para desenvolvimento, chaves SSH e certificados self-signed resolvem local — mas nunca em produção.

Dados sensíveis no código — classificação e higiene

O Domínio 2 dedica uma task inteira a isso. Classificação: PII (identifica a pessoa — CPF, e-mail) e PHI (dados de saúde) exigem tratamento reforçado — criptografia, acesso mínimo, mascaramento em logs. As regras práticas de prova: (1) variáveis de ambiente da Lambda são criptografadas com KMS — use uma CMK própria e helpers de criptografia para valores sensíveis, ou melhor, busque do Secrets Manager em runtime; (2) nunca logar dados sensíveis — sanitize antes de logar (a questão do "CPF aparecendo no CloudWatch Logs" se resolve no código, redigindo o campo); (3) segredo commitado no Git = revogar e rotacionar imediatamente (remover do histórico não basta — a chave já vazou).

Checkpoint de revisão

  • GenerateDataKey → cifrar localmente com a data key em claro → descartar a chave em claro e armazenar a data key criptografada junto do dado (envelope encryption). Encrypt direto só aceita 4 KB.
  • Secrets Manager com rotação automática habilitada (integração nativa com RDS) — a aplicação busca o segredo em runtime pelo SDK.
  • Role na conta B com trust policy para a conta A; a aplicação chama STS AssumeRole e usa as credenciais temporárias retornadas.

SAM — CloudFormation para serverless

O SAM é uma transformação do CloudFormation (Transform: AWS::Serverless-2016-10-31) com recursos abreviados: AWS::Serverless::Function, ::Api, ::SimpleTable. Alta prioridade

Os três pilares e quem responde o quê

PerguntaServiço
"Como estão meus recursos/apps?" (métricas, logs, alarmes)CloudWatch
"Por onde passou e onde travou ESTA requisição?" (tracing)X-Ray
"Quem chamou qual API na conta?" (auditoria)CloudTrail

CloudWatch para devs — os detalhes cobrados

Métricas custom via PutMetricData, com namespace e dimensions; resolução padrão de 1 minuto e high-resolution até 1 segundo (para alarmes de reação rápida). Em EC2, memória e disco usado NÃO são métricas nativas — exigem o CloudWatch Agent. Nos Logs: metric filters transformam padrões de log em métricas (ex.: contar "ERROR" e alarmar), subscription filters transmitem logs em tempo real para Lambda/Kinesis, e o Logs Insights consulta com query language. Lambda loga stdout automaticamente (permissões via execution role).

EMF e structured logging — citados nominalmente no guide

EMF (Embedded Metric Format): a aplicação escreve o log em um formato JSON especial e o CloudWatch extrai métricas automaticamente dele — métrica custom de alto volume sem chamadas PutMetricData (que custam e têm cota). É a resposta para "emitir métricas custom da Lambda com o menor custo/latência". Structured logging: logar JSON com campos consistentes (requestId, userId, nível) em vez de texto livre — é o que torna o Logs Insights realmente útil (filter userId = "x") e é a "estratégia de logging eficaz" que a Task 4.2 pede. Complemento: diferencie logging (o que aconteceu), monitoring (métricas e alarmes sobre saúde) e observability (os três pilares juntos — logs, métricas e traces — para explicar o desconhecido).

X-Ray — instrumentação

ConceitoO que saber
Segments / SubsegmentsUnidades do trace (serviço / chamadas internas, ex.: query no DynamoDB)
Annotations vs MetadataAnnotations são indexadas (filtráveis: annotation.userId="123"); metadata NÃO é indexada (só contexto)
SamplingRastrear uma fração das requisições para controlar custo (regra padrão: 1ª req/s + 5%)
X-Ray daemonProcesso que recebe os segmentos via UDP 2000 e envia à API — em EC2/ECS você o executa (sidecar); no Lambda basta ativar Active Tracing
🪤
Armadilha annotation/metadata"Filtrar traces por ID do cliente" = annotation (indexada). Guardaram em metadata e a busca não encontra — esse é o bug da questão. E "X-Ray não recebe dados do container" = daemon ausente/porta UDP 2000 bloqueada ou falta da policy AWSXRayDaemonWriteAccess.

Checkpoint de revisão

  • Metric filter no log group contando o padrão + alarme do CloudWatch sobre a métrica gerada (com SNS para notificar).
  • Métrica high-resolution (PutMetricData com StorageResolution=1) + alarme de alta resolução (períodos de 10s/30s).
  • Annotation — é indexada e utilizável em filter expressions; metadata serve só para carregar contexto adicional não pesquisável.
  • CloudTrail — registra as chamadas de API de gerenciamento (DeleteTable), com identidade, origem e horário.
