# CloudPath internationalization architecture

CloudPath supports Brazilian Portuguese (`pt-BR`) as the canonical source locale and English (`en`) as a production locale.

The localization system preserves the existing Vanilla JS architecture, premium visual implementation, study semantics, CloudArena mechanics and Portuguese narration assets. It intentionally avoids maintaining duplicated PT and EN applications.

## Product contract

- `pt-BR` is the canonical source of product and certification content.
- `en` is a supported product locale for public UI, study trails, practice exams and CloudArena.
- English narration is intentionally disabled. Portuguese MP3s must never be presented as English audio.
- `assets/narracao/**` is outside the localization scope unless a separate narration project is explicitly approved.
- Partial exam translations are staging only and are never served at runtime.
- Structural truth is never authored by a translator: question IDs, domains, answer indexes, `selectCount`, topics and CloudArena identity remain canonical.
- CloudArena alternative identity is the stable `optionId`, never literal option text.
- Runtime production does not depend on an AI/translation API.

---

## 1. Runtime locale engine

Core runtime:

```text
js/i18n.js
```

It provides:

- `pt-BR` and `en`
- persisted locale selection
- `?lang=` override
- route-derived English locale for `/en/...`
- Portuguese fallback
- `<html lang>` synchronization
- `cloudpath:i18nready` and `cloudpath:localechange` events
- semantic translation for text, placeholders, `aria-label` and `title`
- modular catalog loading and merge

Page adapters consume the shared locale state rather than implementing independent language state:

```text
js/i18n-home.js
js/i18n-shared.js
js/i18n-simulados.js
js/i18n-cloudarena.js
js/i18n-internal-literals.js
js/i18n-trail-content.js
```

Do not create a second locale controller inside individual features.

## 3. Indexable English routes

English routes reuse the same source HTML rather than duplicated `*-en.html` files.

Examples:

```text
/                         -> PT home
/en/                     -> EN home
/simulados.html          -> PT practice exams
/en/simulados.html       -> EN practice exams
/cloudarena.html         -> PT CloudArena
/en/cloudarena.html      -> EN CloudArena
/trilha-saa.html         -> PT SAA trail
/en/trilha-saa.html      -> EN SAA trail
```

The route migration is defined by:

```text
scripts/apply_indexable_en_routes.py
```

The route layer handles:

- `lang="en"`
- localized public metadata
- canonical URLs
- `hreflang="pt-BR"`
- `hreflang="en"`
- `hreflang="x-default"`
- EN sitemap entries when `sitemap.xml` exists
- same-origin internal-link synchronization with active locale

## 4. Practice exam source of truth

Canonical PT banks:

```text
data/exams/<certification>/<level>.json
```

Ready EN banks:

```text
data/exams-en/<certification>/<level>.json
```

Human-language staging:

```text
translations/en/<certification>/<level>/*.json
```

A staging question may contain only human-language fields:

```text
text
options
explanation
hint                 # when present in PT
optionRationales     # when present in PT
```

The following fields remain canonical and are never supplied by translation staging:

```text
id
domain
correct
selectCount
topics
certCode
level
```

A complete EN target is promoted only when staged question IDs exactly match the canonical PT bank.

## 5. Offline translation pipeline

CloudPath does not depend on a hosted inference API for translation generation.

The reusable local engine is:

```text
scripts/offline_mt.py
```

Default checkpoint:

```text
Helsinki-NLP/opus-mt-roa-en
```

It is downloaded by CI and executed locally on the GitHub Actions runner with CPU PyTorch/Transformers. It is a build-time authoring aid only and is not part of CloudPath runtime.

### Immutable technical anchors

AWS/service names, technical acronyms, URLs, placeholders and numeric facts are extracted before translation and are **not sent through the model**. Only natural-language spans between those anchors are translated. The original anchors are then reassembled literally.

A second post-translation integrity check verifies the result.

This avoids failures such as accidentally replacing one distractor service with another or altering durations, percentages, pricing numbers or AWS terminology.

### Exam staging

```text
scripts/translate_exam_staging_offline.py
.github/workflows/translate-exam-staging.yml
```

Request manifests live under:

```text
translations/requests/
```

The generator can write staging only. It cannot publish `data/exams-en/**`.

### Semantic repair

```text
scripts/repair_exam_staging_offline.py
.github/workflows/repair-exam-staging.yml
```

The repairer scans existing staging using field-local integrity rules and retranslates only fields that violate the PT source anchors. Good existing prose is left untouched.

It is transactional: every repaired candidate is validated before any staging file is written.

## 6. Field-local translation integrity

Mechanical semantic fidelity is implemented by:

```text
scripts/translation_integrity.py
scripts/validate_english_translation_quality.py
```

Integrity is checked **per field**, not merely per question.

For example, if canonical PT `option[2]` contains `Spot`, the corresponding EN `option[2]` must also contain that technical anchor. Mentioning `Spot` in another option or explanation does not satisfy the contract.

The same rule applies to:

- question text
- each answer option
- explanation
- hint
- each option rationale
- numbers, percentages and durations

The quality gate also rejects:

- empty translations
- option/rationale cardinality changes
- obvious Portuguese residue
- long PT prose copied unchanged into EN

The main promotion workflow executes this semantic fidelity gate **before** EN banks are promoted to `ready`.

## 7. Builders and validators

Core exam tools:

```text
scripts/build_exam_translation.py
scripts/validate_exam_translation_staging.py
scripts/validate_exam_locale_parity.py
scripts/validate_english_translation_quality.py
scripts/promote_complete_exam_translations.py
```

Ready-bank parity validates, among other things:

- question ID/count
- domain membership
- correct answer indexes
- `selectCount`
- topics
- option count/order
- structural domain metadata

The production matrix requires 12 ready EN banks:

```text
CLF-C02  iniciante / medio / avancado
DEA-C01  iniciante / medio / avancado
DVA-C02  iniciante / medio / avancado
SAA-C03  iniciante / medio / avancado
```

Each ready bank must contain:

```json
{
  "_translation": {
    "locale": "en",
    "sourceLocale": "pt-BR",
    "status": "ready"
  }
}
```

## 8. Locale-aware practice exam runtime

The backend resolves exam content by locale with a safe PT fallback.

EN content is selected only from a corresponding bank marked `ready`. The resolved content locale is stored in the active exam/live-room session, preventing language changes in the middle of a running exam.

Clients propagate locale from:

```text
js/simulados.js
js/socket-client.js
js/simulado-live-host.js
```

## 9. CloudArena stable identity

CloudArena no longer uses option text as identity.

Canonical option ID:

```text
<questionId>:option:<zero-based-index>
```

Example:

```text
clf-ini-001:option:2
```

`matchText` remains readable metadata only. Editing or translating an option does not change its identity.

Migration/validation:

```text
scripts/prepare_arena_option_ids.py
scripts/validate_arena.py
```

## 10. CloudArena EN content

Ready pedagogical overlays:

```text
data/cloudarena/breakdowns-en/<certification>.json
```

The production matrix requires ready overlays for:

```text
clf-c02
dea-c01
dva-c02
saa-c03
```

Offline staging authoring:

```text
scripts/translate_arena_staging_offline.py
.github/workflows/translate-arena-staging.yml
```

Only pedagogical prose such as wrong-answer reasons and final-blow justifications is translated. `questionId`, `optionId`, stages and correct flags remain canonical.

An EN Arena is served only when its EN overlay and all three EN exam banks for the certification are ready. Otherwise the Arena falls back as a whole to PT, avoiding mixed-language battles.

## 11. CloudArena visual UI

The combat engine is not duplicated or rewritten.

```text
js/i18n-cloudarena.js
```

loads paired visual literal catalogs and translates visible text, ARIA labels, titles, placeholders and known dynamic labels. A MutationObserver covers UI fragments recreated by combat state changes.

Catalog authoring:

```text
scripts/generate_cloudarena_literal_catalog.py
.github/workflows/generate-cloudarena-literals.yml
```

The generator uses the same offline translation engine.

## 14. Narration contract

Portuguese narration remains available in PT-BR.

When locale is EN, `js/tts-reader.js`:

- stops active narration
- closes/hides narration controls
- prevents narration keyboard shortcuts
- clears/prevents audio source loading
- avoids MP3 preload/download
- resets Media Session state
- exposes the disabled state in English UI

`assets/narracao/**` must remain unchanged by this i18n project. Final assurance compares that path against the base branch.

---

## 15. Time-sensitive AWS facts

Localization is not allowed to freeze known-obsolete AWS facts into EN content.

Targeted current-fact checks live in:

```text
scripts/validate_aws_current_facts.py
scripts/apply_aws_2026_content_fixes.py
scripts/apply_aws_2026_extra_fixes.py
```

Canonical PT is corrected first, then EN is rebuilt/repaired from the updated source. Deliberately incorrect distractors may still describe old behavior when that is pedagogically intentional.

## 16. CI and final assurance

Important workflows include:

```text
.github/workflows/validate-banks.yml
.github/workflows/translation-quality.yml
.github/workflows/generate-internal-literals.yml
.github/workflows/generate-cloudarena-literals.yml
.github/workflows/generate-trail-literals.yml
.github/workflows/indexable-en-routes.yml
.github/workflows/i18n-final-assurance.yml
```

The final assurance requires, in one integrated run:

- relevant JS/Python syntax
- canonical PT banks
- staging contracts
- field-local translation integrity
- 12/12 EN exam banks ready
- EN/PT exam structural parity
- current AWS fact guards
- stable CloudArena `optionId`
- 4/4 EN CloudArena overlays ready
- CloudArena EN/PT parity
- locale catalog parity
- internal/CloudArena/trail adapter wiring
- absence of executable dependency on the retired GitHub Models inference API
- EN narration disabled
- narration assets unchanged
- indexable `/en` routes and hreflang
- HTTP smoke tests for EN pages, Simulados and all four CloudArena APIs

The assurance report is uploaded as a workflow artifact for the exact tested commit. The workflow does **not** make a follow-up commit, so the SHA that turns green is the SHA that was actually validated.

## 17. Adding a future certification

1. Add/validate the canonical PT bank.
2. Create EN staging under `translations/en/<cert>/<level>/` using the offline generator or reviewed manual translation.
3. Run staging and semantic fidelity validation.
4. Reach exact 100% ID coverage for each level.
5. Promote through `promote_complete_exam_translations.py`.
6. Confirm ready-bank parity.
7. Add/migrate CloudArena overlays to stable `optionId` where applicable.
8. Generate/review EN pedagogical overlay staging offline.
9. Build and validate the ready EN Arena overlay.
10. Add any new UI/trail literals to paired PT/EN catalogs.
11. Run the final assurance workflow before merge.

Do not bypass staging, manually edit answer-key metadata into EN, or expose a partial target at runtime.
