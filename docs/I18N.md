# CloudPath internationalization architecture

CloudPath supports Brazilian Portuguese (`pt-BR`) as its canonical source locale and English (`en`) as a production locale.

The localization system was designed to preserve the existing Vanilla JS architecture, premium visual implementation, question-bank semantics, CloudArena game logic and Portuguese narration assets. It intentionally avoids duplicating the application into separate PT and EN codebases.

## Product contract

- `pt-BR` remains the canonical source language.
- `en` is a complete product locale for the UI, study trails, practice exams and CloudArena content.
- English narration is intentionally disabled. No Portuguese narration is presented as English audio.
- `assets/narracao/**` is outside the current localization scope and must remain untouched unless an explicit future narration project is approved.
- English content is promoted only after structural validation.
- A partially translated exam bank is never served to users.
- Question IDs, domains, answer indexes, topics and structural metadata never come from a translation model.
- CloudArena option identity is based on stable `optionId`, never literal answer text.

---

## 1. Runtime locale engine

Core runtime:

```text
js/i18n.js
```

The runtime provides:

- `pt-BR` and `en`
- persisted language preference
- `?lang=` override
- Portuguese fallback
- `<html lang>` synchronization
- locale events
- semantic translation for text, placeholders, `aria-label` and `title`
- modular locale catalogs composed with deep merge

Important events:

```text
cloudpath:i18nready
cloudpath:localechange
```

Page adapters subscribe to these events rather than creating independent locale state.

Main adapters:

```text
js/i18n-home.js
js/i18n-shared.js
js/i18n-simulados.js
js/i18n-cloudarena.js
js/i18n-internal-literals.js
js/i18n-trail-content.js
```

Do not add a second language-state implementation inside individual modules. Use `window.I18n` and the shared events.

## 3. Indexable English routes

English pages are served from the same source HTML through `/en/...` routes.

Examples:

```text
/                         -> PT home
/en/                     -> EN home
/trilha-saa.html         -> PT SAA study path
/en/trilha-saa.html      -> EN SAA study path
/simulados.html          -> PT practice exams
/en/simulados.html       -> EN practice exams
/cloudarena.html         -> PT CloudArena
/en/cloudarena.html      -> EN CloudArena
```

The route implementation is applied by:

```text
scripts/apply_indexable_en_routes.py
```

It adds:

- English route handling in `server.js`
- locale synchronization in `js/i18n.js`
- `<html lang="en">` for `/en/...`
- localized title/description metadata for public pages
- canonical URLs
- `hreflang="pt-BR"`
- `hreflang="en"`
- `hreflang="x-default"`
- English sitemap entries when `sitemap.xml` is present

Internal same-origin HTML links are synchronized with the active locale so users do not silently jump between PT and EN while navigating.

Do not create `*-en.html` copies. The route layer is intentionally single-source.

## 4. Practice-exam translation pipeline

Canonical PT banks:

```text
data/exams/<certification>/<level>.json
```

Ready English banks:

```text
data/exams-en/<certification>/<level>.json
```

Human-language staging:

```text
translations/en/<certification>/<level>/*.json
```

A staging file may contain only translatable fields:

```text
text
options
explanation
hint                 # when present in PT
optionRationales     # when present in PT
```

The following structural fields are never authored by the translator:

```text
id
domain
correct
selectCount
topics
certCode
level
```

### Builder and validators

```text
scripts/build_exam_translation.py
scripts/validate_exam_translation_staging.py
scripts/validate_exam_locale_parity.py
scripts/promote_complete_exam_translations.py
scripts/validate_english_translation_quality.py
```

A complete target is promoted only when staged question IDs exactly match the canonical PT bank.

Ready-bank parity validates, among other things:

- question IDs and count
- domain IDs and membership
- `correct` indexes
- `selectCount`
- topics
- option count/order
- structural domain metadata

### Assisted translation

The repository includes a guarded GitHub Models staging generator:

```text
scripts/translate_exam_staging_with_github_models.py
.github/workflows/translate-exam-staging.yml
```

Request manifests live under:

```text
translations/requests/
```

The model is allowed to generate human-language staging only. It has no authority to publish a ready bank and cannot provide answer-key metadata.

The workflow explicitly fails if the staging generator modifies `data/exams-en/**`.

### Current ready matrix

The bilingual assurance contract requires all 12 banks:

```text
CLF-C02  iniciante / medio / avancado
DEA-C01  iniciante / medio / avancado
DVA-C02  iniciante / medio / avancado
SAA-C03  iniciante / medio / avancado
```

All must have:

```json
{
  "_translation": {
    "locale": "en",
    "sourceLocale": "pt-BR",
    "status": "ready"
  }
}
```

## 5. Locale-aware practice-exam runtime

The backend resolves exam content by locale while preserving safe fallback behavior.

English content is used only when a corresponding ready bank exists.

The session stores its resolved content locale so changing the UI preference does not mutate the language of questions already loaded into an active exam.

The client sends the selected locale from:

```text
js/simulados.js
js/socket-client.js
js/simulado-live-host.js
```

The server exposes locale/fallback metadata in relevant responses.

Do not load a partially staged file directly from `translations/**` at runtime.

## 6. CloudArena stable identity

Historical behavior linked overlay metadata to answer text using `matchText`.

That was intentionally removed because editing or translating an answer could silently break the Arena.

The current identity contract is:

```text
<questionId>:option:<zero-based-index>
```

Example:

```text
clf-ini-001:option:0
clf-ini-001:option:1
clf-ini-001:option:2
clf-ini-001:option:3
```

Migration/validation:

```text
scripts/prepare_arena_option_ids.py
scripts/validate_arena.py
scripts/apply_arena_option_id_runtime.py
```

`matchText` remains in the breakdown JSON for readability and is synchronized to the current canonical text when writing, but it is not an identity key.

CloudArena runtime resolution must remain `optionId` based.

- `questionId`
- `optionId`
- `stage`
- correct flags
- answer indexes
- domain metadata

The current ready overlay matrix is:

```text
clf-c02
dea-c01
dva-c02
saa-c03
```


```text

```

English CloudArena is served only when both the EN overlay and all three EN exam banks for that certification are ready. Otherwise the entire Arena falls back to PT rather than producing a mixed-language battle.

The client sends its locale in the Arena API request through the migration in:


## 8. CloudArena visual UI

The game engine and visual effects are not rewritten for localization.

Visible UI literals are extracted from the real HTML/JS and stored in paired catalogs:

```text
scripts/generate_cloudarena_literal_catalog.py
locales/<locale>/cloudarena-literals.json
```

The reactive adapter:

```text
js/i18n-cloudarena.js
```

supports:

- visible text nodes
- `aria-label`
- `title`
- `placeholder`
- dynamically recreated DOM through `MutationObserver`
- common dynamic labels such as level, question, health, points, score, damage, time and streak

It deliberately does not change IDs, selectors, classes, combat state or animations.

## 11. Narration boundary

Portuguese narration remains available in `pt-BR`.

When locale is `en`, `js/tts-reader.js` must:

- stop active narration
- close/hide narration controls
- prevent keyboard narration shortcuts
- clear/prevent audio source loading
- avoid MP3 preload/download
- reset Media Session state
- expose the disabled state in the English UI

The current scope deliberately does not generate English audio.

Any future English-narration project should be a separate change with its own assets, review and delivery contract.

The final assurance workflow compares `assets/narracao/**` against the base branch and fails if those assets changed during this i18n project.

## 12. Time-sensitive AWS facts

Certification content can become stale as AWS pricing, Free Tier, support plans and product behavior evolve.

Current-fact tools:

```text
scripts/apply_aws_2026_content_fixes.py
scripts/apply_aws_2026_extra_fixes.py
scripts/validate_aws_current_facts.py
```

The validator is intentionally narrow and checks only claims that were verified against current AWS primary documentation.

Wrong distractors are allowed to describe obsolete concepts when the purpose of the question is to identify them as wrong. The validator therefore checks truth-bearing fields such as question context, explanation and correct options rather than treating every distractor as a statement of current truth.

When adding a new time-sensitive rule:

1. verify the fact against current AWS primary documentation;
2. update the canonical PT source first;
3. preserve structural question invariants;
4. rebuild/promote the EN bank;
5. add a targeted validator rule when the same outdated claim is likely to recur.

Do not silently "correct" certification facts only in English.

## 14. Final assurance contract

A passing bilingual implementation is represented by:

```text
reports/i18n-assurance.json
```

The report is generated only after the integrated assurance job passes checks that include:

- relevant JavaScript syntax
- Python tool syntax
- canonical PT bank validation
- EN staging validation
- EN/PT exam parity
- mechanical English translation QA
- current AWS fact guardrails
- stable CloudArena option IDs
- PT CloudArena validation
- PT/EN CloudArena structural parity
- locale catalog parity
- expected HTML adapter wiring
- 12/12 ready EN exam banks
- 4/4 ready EN CloudArena overlays
- EN narration disabled
- narration assets unchanged
- indexable `/en/...` route markers and hreflang
- real HTTP smoke tests for EN pages, Simulados and all four CloudArena certification payloads

A report with `status: "passed"` is evidence for technical completion of the bilingual architecture.

It is not a substitute for browser-rendered visual QA.

## 15. Visual QA before production merge

The automated pipeline validates behavior, syntax, content contracts and HTTP delivery, but it cannot prove pixel-level layout quality.

Before merging/deploying a major localization update, manually review at minimum:

### Desktop

- home PT and EN
- navbar language switch
- login modal
- Simulados setup, active exam and result screens
- CloudArena setup, battle and result states
- all four study paths
- Progresso and Histórico
- Host and Player flows

### Mobile

Repeat the same critical surfaces at narrow viewport widths and verify:

- no clipped text
- no horizontal overflow
- buttons remain tappable
- navbar/menu remains usable
- longer English labels do not collide with icons
- cards preserve spacing/hierarchy
- CloudArena HUD remains legible
- study-guide headings and callouts wrap correctly

### Locale switching

Check both directions:

```text
PT -> EN
EN -> PT
```

and test switching while:

- navigating between pages
- configuring a practice exam
- an exam session is active
- viewing a study path
- entering CloudArena

Narration controls must disappear/disable in EN and return in PT without downloading English audio.

## 16. Adding a future certification

Recommended order:

1. add and validate canonical PT banks under `data/exams/<cert>/`;
2. create stable question IDs and topics;
3. add CloudArena overlays using `optionId` when applicable;
4. create EN staging request(s);
5. run staging validation;
6. reach 100% coverage for a level;
7. let the promotion pipeline build the ready EN bank;
8. validate EN/PT structural parity;
9. translate CloudArena pedagogical overlay only after ready EN exam content exists;
10. add/update trail content if the certification has a study path;
11. run final assurance;
12. perform browser visual QA before production merge.

Do not bypass staging by hand-authoring a ready EN bank unless there is a documented emergency and full parity validation still passes.

---

## 17. Design principle

The localization system should remain a **content and routing layer around the existing product**, not a second implementation of CloudPath.

If an i18n change requires rewriting animations, replatforming the frontend, duplicating large HTML pages, changing answer identities, or mixing Portuguese and English content in one session, treat that as an architectural warning and revisit the approach before shipping.
